# Planner 节点问题深度分析

> 分支: `feature/planner-redesign`
> 日期: 2026-05-24
> 状态: 待用户审阅

---

## 1. 当前架构速览

### 1.1 数据流

```
research_data ────┐
recommendation_data ─┤
user_profile ──────┤──→ planner_node ──→ plan_data (PlannerOutput) ──→ END
messages ──────────┘
```

### 1.2 输出结构

```
PlannerOutput
  ├── days: List[DayPlan]
  │     ├── day: int
  │     ├── date: Optional[str]
  │     └── activities: List[Activity]
  │           ├── time: str          # "09:00-11:30"
  │           ├── place: str         # "浅草寺"
  │           ├── type: Literal["attraction","dining","transport","rest","accommodation"]
  │           ├── description: str
  │           ├── duration_min: int
  │           └── transport: Optional[str]  # 到下一活动的方式
  ├── total_budget_estimate: Optional[str]
  └── notes: List[str]
```

### 1.3 路由

```
manager → planner → END
```

Planner 是唯一直接连到 END 的业务节点（Recommender 走 `recommender → reply → END`）。

## 2. 问题分析

### 2.1 一次性生成，无法精准修改 (问题一)

**现象**：每次 `planner_node` 被触发，LLM 接收全部 research_data + recommendation_data + user_profile，在一次调用中生成完整的 `PlannerOutput`（所有天、所有活动）。

**弊端**：

1. **修改粒度失控**。用户说"第三天午餐换一家餐厅"，系统必须重新生成全部 7 天的行程。LLM 可能在重新生成时改变第一天、第二天的内容——即使用户根本没要求改那些。这不是"修改"，这是"重做"。

2. **不可维护**。一个真实旅行计划的生命周期可能是多轮对话的持续打磨：
   - 第 1 轮：生成大体框架
   - 第 2 轮：用户调整第三天的景点顺序
   - 第 3 轮：用户更换住宿地点
   - 第 4 轮：用户补充预算约束
   
   当前架构下，每一轮都是全量覆盖。Planner 没有"增量更新"或"定向修改"的语义。`plan_data` 字段是一个简单的 `Optional[PlannerOutput]`，写入即覆盖，不保留历史版本，不支持 diff，不提供修改回滚。

3. **与其他节点的设计哲学不一致**。`recommendation_data` 是按维度累积的（Recommender 每次写一个维度，Annotated reducer 合并），`research_data` 是通过 Annotated reducer 增量合并的。唯独 `plan_data` 是粗暴的全量覆盖。

**根因**：`PlannerOutput` 是一个扁平的大对象，没有"可寻址"的子结构。你想改 `days[2].activities[3]`，但没有机制能只重写这一个位置而保留其余部分不变。

---

### 2.2 LLM 忽略细节约束 (问题二)

**现象**：Planner 的 prompt（`_PLANNER_TEMPLATE`）一次性注入：

- 对话历史（最多 10 轮）
- 用户画像（可能包含多个目的地、复杂的 Flex 约束）
- 研究数据摘要（可能很大）
- 推荐结果（多个维度的推荐项）

**弊端**：

1. **注意力稀释**。当上下文包含数千 token 的异构信息时，LLM 的注意力会自然倾向于"把行程写出来"而不是"逐条验证约束"。用户提到的偏好（如"不喜欢太拥挤的地方""对海鲜过敏"）在长上下文中容易被淹没。

2. **约束丢失**。当前 prompt 虽然有"从推荐中选取"的指令，但没有结构化的约束检查机制。LLM 不需要（也无法）逐条确认：
   - 每个活动是否来自研究数据
   - 每段交通时间是否合理
   - 每个预算项是否在限制内
   - 每个偏好是否被满足

3. **没有事后校验**。Planner 输出直接写入 `plan_data` 并返回给前端，中间没有任何验证步骤。Critic 节点只存在于 Research Loop 中，Planner 没有对应的质检环节。

**根因**：Planner 的设计假设是"一次性摄入全部信息 → 一次性输出完整计划"。这在信息量少时可以工作，但随着约束增多（多目的地、多偏好、多人数的复杂行程），LLM 的注意力瓶颈会成为信息丢失的主要来源。

---

### 2.3 全量覆盖而非会话级维护 (问题三)

**现象**：`plan_data` 是一个单一值，每次 Planner 执行都完整覆盖。没有任何增量更新、版本管理或局部修改的能力。

**弊端**：

1. **没有"计划即会话"的概念**。在一个合理的旅行规划 Agent 中，Plan 应该是会话的核心产物，从第一轮对话开始就存在（即使是空壳），随着调研和推荐的推进逐步填充，并在后续对话中被反复引用和修改。当前架构中 Plan 是"最后一步生成的静态结果"。

2. **Manager 路由与 Plan 的关系断裂**。当前 Manager 的决策逻辑完全基于 research/recommendation 状态，不感知 Plan 的存在。一旦 Plan 生成，用户再发消息时 Manager 无法判断"用户是在对已有 Plan 提修改意见"还是"用户有新的推荐需求"。这导致：
   - 用户在 Plan 生成后说"换一下第三天的酒店" → Manager 可能路由到 recommender（错误），而不是对 Plan 的局部修改
   - 实际上当前 Manager 根本无法识别这种修改意图，因为 `plan_data` 不在 Manager 的读取列表中

3. **缺乏 Plan 生命周期管理**。Plan 应该有明确的状态机：
   ```
   EMPTY → DRAFT (框架) → DETAILED (填充详情) → CONFIRMED (用户确认) → MODIFIED (修改中)
   ```
   当前没有这个状态机，`is_plan_complete` 只是一个布尔值。

**根因**：`plan_data` 在 TravelState 中被设计为一个"最终交付物"而非"会话中持续演化的核心对象"。STATE_SPEC.md 中明确写着 `plan_data` 的读取者是 "API response only"——这意味着除了返回给前端之外，没有任何节点会读取 Plan 来做后续决策。

---

### 2.4 缺乏时间维度和空间维度 (问题四)

**现象**：当前 `DayPlan` 和 `Activity` 的结构对时间和空间的处理是浅层的。

**时间维度的缺失**：

当前每个 Activity 有一个 `time: str` 字段（如 "09:00-11:30"），但这只是字符串标注，不是结构化时间。问题：

1. **无法做时间约束检查**。假设用户说"我每天不想早于 9 点出发"，当前系统无法自动验证 Plan 是否满足这个约束——因为 `time` 是自由文本，不是 `start_time` + `end_time` 的结构化字段。

2. **无法做时间冲突检测**。如果 LLM 错误地在同一天安排了两个时间重叠的活动，系统无法自动发现。

3. **无法导出时间线视图**。要让前端渲染一条清晰的时间轴（timeline），需要从 `time` 字符串中解析起止时间，这是脆弱且不可靠的。

**空间维度的缺失**：

当前 `Activity.transport` 字段只标注了"从这个活动到下一个活动的交通方式"，但：

1. **没有位置结构化信息**。`place` 是自由文本（如"浅草寺"），没有经纬度、没有区域归属。系统无法计算两个活动之间的实际距离，也无法验证交通时间的合理性。

2. **无法构建空间流**。一个多目的地旅程涉及多个城市/区域之间的移动，当前结构没有：
   - 城市级位置变迁（Day 1-3 在东京，Day 4 在京都）
   - 住宿地点的锚定（每晚住在哪里决定了当天的活动半径）
   - 区域归属分组（今天上午的活动都在台东区，下午转移到涩谷区）

3. **多目的地规划能力弱**。当用户说"先去东京3天，然后去大阪2天"时：
   - `UserProfile.destination` 是 `["东京", "大阪"]` 的列表
   - 但 Planner 的 prompt 没有显式的"城市切换日"概念
   - LLM 在生成 Day 3 和 Day 4 时，不会被告知"这一天你要换城市"
   - 城际交通（新干线/飞机）的安排没有结构化的位置来标记

**根因**：当前数据模型将行程视为"每日活动列表的集合"，而非"沿时间轴展开的空间移动轨迹"。一个直观的旅行计划应该同时回答两个问题：

- **时间轴**：在什么时间点，我在哪里，做什么？
- **空间流**：我从哪里出发，经过哪些地方，最终到达哪里？

当前的 `DayPlan → [Activity, Activity, ...]` 扁平结构无法同时清晰回答这两个问题。

## 3. 问题汇总

| # | 问题 | 严重度 | 影响范围 |
|---|------|--------|---------|
| 1 | 一次性全量生成，无法精准修改单项 | 高 | 用户体验、多轮对话能力 |
| 2 | LLM 长上下文导致细节约束丢失 | 高 | 计划准确性、用户信任 |
| 3 | 全量覆盖更新，非会话级维护 | 高 | 多轮对话一致性、Manager 路由 |
| 4 | 缺乏时间+空间二维结构化 | 高 | 多目的地规划、行程可视化 |

这四个问题互相耦合：
- 如果解决了 #4（时间和空间结构化），则 #1 和 #3 可以借助结构化的索引来精准定位要修改的条目
- 如果解决了 #1（增量修改），则需要 #3 的 Plan 生命周期来管理修改状态
- 如果解决了 #2（约束丢失），则需要 #4 的结构化使得约束检查可以自动化

## 4. 重构方向建议 (初步)

以下仅为方向性建议，待用户确认后进入详细设计：

1. **Plan 数据模型重构**：引入 `Timeline`（时间轴）和 `SpatialFlow`（空间流）两个核心抽象，使 Plan 从"活动列表"升维为"沿着时间轴的空间轨迹"。

2. **Plan 增量更新机制**：支持对 Plan 的定向修改（替换某天某活动、调整某天住宿），而非全量覆盖。

3. **Plan 生命周期**：Plan 在整个会话中持续存在和维护，而非仅在最后一步生成。Manager 能识别"修改计划"类意图。

4. **Plan 与推荐/研究的双向关联**：Plan 中的每个活动应能回溯到其来源（来自哪个推荐项、哪条研究数据），支撑溯源和修改。

5. **路由调整**：Planner 不应直接到 END，而应经过类似 Recommender → Reply 的流程，让用户能对 Plan 做出反馈。
